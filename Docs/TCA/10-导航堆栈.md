# 导航堆栈

对照源码：`TCA/ContactDetailFeature.swift`、`TCA/ContactDetailView.swift`、`TCA/EditContactFeature.swift`、`TCA/EditContactView.swift`、`TCA/ContactsFeature.swift`、`TCA/ContactsView.swift`

教程原文：[Navigation stacks](https://pointfreeco.github.io/swift-composable-architecture/1.10.0/tutorials/composablearchitecture/02-04-navigationstacks)

这一课在联系人列表上加一条钻进去的路径。点一行进入详情，详情里可以再推进编辑页，也可以确认删除。删除后回到列表，并且这个人从列表消失。编辑保存后，列表和还留在堆栈里的详情都会换成新名字。

sheet 和 alert 仍然用上一课的 `destination`。堆栈是另一条轴，两者可以同时存在：人在详情页里，也可以再弹出一个 sheet。所以 `path` 不放进 `Destination` 枚举。

## 和弹窗的差别

| | 弹窗 `destination` | 堆栈 `path` |
|---|---|---|
| 同时能有几个 | 零个或一个 | 零个到很多个，一层叠一层 |
| 状态类型 | 可选枚举 | `StackState`，带 id 的数组 |
| 连接器 | `ifLet` | `forEach` |
| 视图 | `.sheet`、`.alert` | `NavigationStack(path:)` |

`StackState` 是 TCA 给导航堆栈准备的集合。每个元素有一个 `StackElementID`，用来指出动作发生在哪一层。

```swift
var path = StackState<Path.State>()

case pathAction(StackActionOf<Path>)
```

`StackActionOf<Path>` 就是 `StackAction<Path.State, Path.Action>`。堆栈上有两种页面，所以元素不是某一种 `State`，而是一个枚举，和弹窗的 `Destination` 同一套做法：

```swift
@Reducer
enum Path {
    case detail(ContactDetailFeature)
    case edit(EditContactFeature)
}
```

数组里可以同时有多层，而且相邻两层可以是不同的 case。例如先推进详情，再从详情推进编辑，`path` 就是 `[.detail(...), .edit(...)]`。

只有一种页面时，元素可以直接写成 `StackState<ContactDetailFeature.State>`，`forEach` 后面要写出 `{ ContactDetailFeature() }`。页面一多，就收成 `@Reducer enum`。这时 `forEach` 不用再写 reducer 闭包，库能从 `Path.State` 反查出来，再按 case 转给对应的子功能。

## 点一行时发生什么

视图使用库提供的 `NavigationLink(state:)`，不要用 SwiftUI 自带的 `init(value:)`。

推进去的值必须是堆栈元素 `Path.State`。`.detail` 标明这一层是详情，而不是编辑：

```swift
NavigationLink(
    state: ContactsFeature.Path.State.detail(
        ContactDetailFeature.State(contact: contact)
    )
) {
    Text(contact.name)
}
```

点下去时，这份状态被追加进 `path`。父功能收到的动作类似：

```text
.pathAction(.push(id:, state: .detail(ContactDetailFeature.State(...))))
```

父功能的 `case .pathAction` 兜底返回 `.none`。真正把页面画出来的是 `NavigationStack`：它观察 `path`，每多一个元素就推进一层。

```swift
NavigationStack(path: $store.scope(\.path, action: \.pathAction)) {
    List { /* 根页面：联系人列表 */ }
} destination: { store in
    switch store.case {
    case let .detail(store):
        ContactDetailView(store: store)
    case let .edit(store):
        EditContactView(store: store)
    }
}
```

`destination` 闭包拿到的是 `Path` 的 Store。`store.case` 把它拆成某一层真正的子 Store。详情视图读不到整个 `path`，也改不了列表。漏写一个 case，这里会编译失败。

1.10 教程里状态和动作都叫 `path`，写成 `$store.scope(state: \.path, action: \.path)`。本工程把动作改成 `pathAction`，1.26 也不再写 `state:` 标签。

用户点系统返回时，Binding 把那一层从 `path` 移除，动作是 `.path(.popFrom(id:))`。

行里面还有删除按钮，所以 `NavigationLink` 加了 `.buttonStyle(.borderless)`，否则整行都算链接，垃圾桶点不到。

## forEach 接上详情 reducer

```swift
.forEach(\.path, action: \.pathAction)
```

`path` 里有三层时，就有三份子 reducer，每层按自己的 case 选择详情或编辑。某个动作带着元素 id 进来，`forEach` 只把这个动作交给那一层，并只修改那一层的状态。

它和 `ifLet` 一样做这几件事：

- 子 reducer 先跑，父 reducer 后跑
- 某一层从 `path` 消失时，取消这一层还在跑的 Effect
- 给这一层注入 `dismiss`。详情页调用 `dismiss()`，就是把自己从堆栈弹掉

## 从详情删除

详情页不认识列表。它的确认动作不带联系人 id，因为这条联系人已经在自己的 `State` 里。

```swift
case .alert(.presented(.confirmDeletion)):
    return .run { send in
        await send(.delegate(.confirmDeletion))
        await self.dismiss()
    }
```

这个动作回到父功能时，外面带着堆栈元素的 id，中间还要经过 `Path` 的 `.detail`：

```text
.pathAction(.element(id: id, action: .detail(.delegate(.confirmDeletion))))
```

父功能用这个 id 取出那一层的详情状态，再删列表里的同一个人：

```swift
case let .pathAction(.element(id: id, action: .detail(.delegate(.confirmDeletion)))):
    guard let detailState = state.path[id: id]?.detail else { return .none }
    state.contacts.remove(id: detailState.contact.id)
    return .none
```

`state.path[id:]` 取出的是 `Path.State?`。`?.detail` 再钻进详情这个 case；这一层如果是编辑页，结果是 nil。

随后子功能的 `dismiss()` 把这一层弹出。先发 delegate、再 dismiss，是为了父功能还能从 `path` 里读到这条联系人。

列表行上的垃圾桶仍然走原来的 `destination = .alert(...)`，不经过堆栈。两种删除各用各的确认框。

## 第二种页面：从详情再推进编辑

详情页没有 `path`，不能自己 `append`。它发 `.delegate(.edit)`，父功能听到后把另一种页面压到上面：

```swift
case let .pathAction(.element(id: id, action: .detail(.delegate(.edit)))):
    guard let detailState = state.path[id: id]?.detail else { return .none }
    state.path.append(.edit(EditContactFeature.State(contact: detailState.contact)))
    return .none
```

这时堆栈是两层：下面是详情，上面是编辑。编辑页保存时同样先发 delegate，再 `dismiss()` 把自己弹掉。父功能做两件事：改列表里的名字，再写回还留在堆栈里的那一层详情。回到详情时，导航标题已经是新名字。

往堆栈里再加第三种页面，就再给 `Path` 加一个 case，并在 `destination` 的 `switch store.case` 里补一个分支。父功能的 `path` 字段不用改类型。
